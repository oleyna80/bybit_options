# Documentation & Governance Audit — 2026-09-02

## Audit baseline

- Repository: `oleyna80/bybit_options`
- Reviewed branch: `main`
- Baseline commit: `e46a944383111a79336b15544436f2e97de2c862`
- Review type: documentation/governance deep review with repository evidence
- Remediation boundary: documentation/control-plane metadata only
- Production code, tests, dependencies, CI, database migrations, runtime secrets,
  and deployment configuration were not modified.

## Executive summary

No confirmed **Critical** documentation finding was identified on the reviewed
baseline. Five **High** findings were confirmed:

1. agent-context ignore rules do not exclude secret/private runtime files that Git
   already ignores;
2. retained legacy agent/governance material still uses mandatory language without
   a local non-authoritative marker;
3. runtime/deployment documentation contains stale facts and commands that can
   reach live exchange/database/runtime surfaces;
4. product/status documentation can be read as stronger trading/live readiness
   than the current production backlog supports;
5. the default branch has no GitHub branch protection or repository ruleset even
   though governance expects external enforcement for consequential Git actions.

The remediation in this Work Block is intentionally narrow: make authority
boundaries explicit, harden agent ignore coverage, replace the operational runtime
reference with repository-verified facts, and add evidence-lifetime/status
semantics. Historical product documents and reports are preserved.

## Severity model

- **Critical** — likely immediate loss of control, secret exposure, destructive/live
  action, or false safety assertion with no meaningful gate.
- **High** — credible path to unsafe execution, authority bypass, secret handling
  error, or materially wrong operational decision.
- **Medium** — material drift/ambiguity that can cause incorrect engineering or
  assurance decisions but normally requires another step before consequential
  impact.
- **Low** — navigation, naming, duplication, or maintainability issue with limited
  immediate operational risk.

## High

### H-01 — `.agentignore` does not exclude secrets/private runtime artefacts

- **File / section:** `.agentignore`; compare `.gitignore`.
- **Problem:** the agent ignore file excludes build/cache/log/CSV paths but does
  not exclude `.env*`, private-key formats, local databases, account-fill files,
  or generated portfolio reports. Git ignore already excludes these classes.
- **Evidence:** `.gitignore` contains `.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`,
  `*.pfx`, local DB formats, `bybit_option_fills_year.json`, and generated risk
  reports; the reviewed `.agentignore` did not.
- **Risk:** an agent/runtime that honors `.agentignore` could ingest credentials,
  account/trading data, or local private state even when those files cannot be
  committed accidentally.
- **Recommended fix:** mirror sensitive/local classes into `.agentignore` as
  defense in depth. Do not treat `.agentignore` as the primary security boundary.
- **Disposition:** **FIXED in this branch**.

### H-02 — Legacy agent/governance files retain normative language without local authority markers

- **Files / sections:** `agreements/**`, `.agent/roles/**`,
  `.agent/workflows/bybit_options_workflow.md`, flat legacy files under
  `.agent/skills/`.
- **Problem:** current `AGENTS.md`, `PROJECT_MAP.md`, and
  `.agent/bootstrap-profile.json` classify these surfaces as historical or
  non-authoritative after `SDLC-MIGRATION-001`, but the retained files themselves
  still contain `MUST`, Task-Auto pauses, old role names, model-routing rules, and
  older path conventions. A reader entering through a legacy file can reasonably
  mistake it for current policy.
- **Evidence:** current authority is Owner -> `AGENTS.md`/`governance/` -> approved
  specification/Work Block, with current roles in `.agent/ROSTER.md` and lifecycle
  in `.agent/workflows/sdd-protocol.md`; legacy agreements use a different routing
  and approval model. `.agent/bootstrap-profile.json` lists folder-form
  `<skill>/SKILL.md` files as installed skills, while flat skill files remain.
- **Risk:** conflicting approval gates, role authority, stop conditions, and
  source-of-truth order; agents can either stop unnecessarily or proceed under the
  wrong rule set.
- **Recommended fix:** preserve historical content but add directory-level
  non-authoritative markers and canonical navigation; do not delete legacy files
  without a separate approved archival scope.
- **Disposition:** **FIXED in this branch** for agreements, roles, workflows and
  skill routing markers.

### H-03 — Runtime/deployment documentation is stale and can trigger live side effects

- **Files / sections:** `docs/ops/running.md`; `README.md` Web Interface/Quick
  Start; `docs/architecture.md`; `INTEGRATION.md` Deployment/Production.
- **Problem:** the old runtime SSOT states frontend port `3002`, references a
  nonexistent `.env.example`, presents direct migration/application commands, and
  describes backend/hedger launch paths without the current live-network caveats.
  `INTEGRATION.md` presents Docker/Gunicorn production commands and production env
  examples as a deployment guide.
- **Evidence:** `frontend/vite.config.ts`, `frontend/Dockerfile`, and
  `docker-compose.yml` use port **3001**. `.env.example` is absent from `main`.
  `bybit_options/api/app.py` requires Bybit credentials and creates
  `BybitConnector(..., testnet=False)` during lifespan, so `BYBIT_TESTNET` does
  not make this API path testnet-safe. `database.py` requires `DATABASE_URL` at
  import. `scripts/run_hedger.py --dry-run` still loads credentials, creates a DB
  pool/connector and starts/stops the bot task. `database_migrations/` contains
  001–010 and 012–014, not only the old 003–005 recipe.
- **Risk:** a developer can run a supposed dev/smoke command against the mainnet
  API or a real DB, apply an incomplete migration sequence, or troubleshoot the
  wrong port.
- **Recommended fix:** make `docs/ops/running.md` a repository-observed runtime
  reference; separate static verification from network/runtime actions; mark
  migration procedure `UNKNOWN` until a canonical migration runner/order is
  established. Treat broad deployment guides as non-authoritative until reviewed
  under deployment/security scope.
- **Disposition:** **FIXED in `docs/ops/running.md`**. `README.md`,
  `docs/architecture.md`, and `INTEGRATION.md` remain intentionally unchanged and
  are explicitly not promoted to operational SSOT by this branch.

### H-04 — Trading/product status can be read as stronger live readiness than current backlog supports

- **Files / sections:** `README.md` Development Status / Trading Bots;
  `docs/tasklist/HEDGER.tasklist.md`; `docs/tasklist/PRODUCT.tasklist.md`.
- **Problem:** README labels the Delta Hedger “Active” and gives high completion
  percentages; HEDGER tasks include completed automatic option purchase/close
  behavior. The current product backlog still has production controls as TODO,
  including production compose/infrastructure, kill switch, position limits,
  24-hour testnet run, authentication, per-user key storage and RLS.
- **Evidence:** `PRODUCT.tasklist.md` marks `HEDGER-017 Kill Switch`,
  `HEDGER-018 Position Limits`, `HEDGER-019 24h Testnet Run`, production infra and
  authentication/key-isolation tasks TODO. The API path also hard-codes mainnet
  connector mode as noted in H-03.
- **Risk:** “Active/Done” can be interpreted as safe-for-live-trading instead of
  “implementation exists”. For a trading-capable service this is a material
  safety/operational distinction.
- **Recommended fix:** separate implementation status, assurance status, and live
  readiness in future product documentation. Do not mark live/production-ready
  until the applicable safety backlog and verification are complete.
- **Disposition:** **PARTIALLY MITIGATED** by new tasklist evidence semantics and
  runtime warnings. Root product status is intentionally not rewritten without a
  product-owner/trading-readiness review.

### H-05 — Default branch lacks external GitHub protection/ruleset enforcement

- **Surface:** GitHub repository settings for `main`; governance Hard Stops.
- **Problem:** governance treats direct protected/default-branch mutation and
  history rewriting as consequential actions and explicitly states that real
  enforcement should come from repository/credential controls, but GitHub reports
  `main` as unprotected and the repository rulesets endpoint returns no rulesets.
- **Evidence:** branch metadata for `main` reports `protected: false`; repository
  rulesets list is empty on the review date.
- **Risk:** the documented cooperative guardrails are not backed by a GitHub-side
  default-branch enforcement boundary. A credential with write capability can
  bypass the intended PR/approval path.
- **Recommended fix:** Owner/repository-admin action: configure branch protection
  or a repository ruleset for `main` (PR-only changes, appropriate review/status
  requirements, force-push/deletion restrictions) proportionate to project risk.
- **Disposition:** **NOT FIXED** — repository settings are outside this
  documentation-only PR.
